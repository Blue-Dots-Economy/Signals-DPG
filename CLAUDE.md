## Core mental model

DPG is a **network-aware** backend. The vocabulary matters and is used consistently in code:

- **network** — the shared contract (e.g. `yellow_dot`, `blue_dot`). Defined by a `network.json` schema.
- **domain** — a role inside a network (e.g. `student`). An instance serves one or more domains via `SERVED_DOMAINS`.
- **instance** — one deployment of the API serving its configured domains.
- **item** — a versioned schema-typed record. `item_type` is a schema identifier like `profile_1.0`, never freeform.
- **action** — an interaction between items. **event** — the structured result.

`item_instance_url` and `item_schema_url` are generated by the backend during item creation; do not let clients set them.

## Lifecycle, U18 gating & reference data (load-bearing behaviours)

Enforced in code and easy to miss from the schema alone:

- **Lifecycle & retire.** Items move `draft → live → paused → retired` via `POST /api/v1/item/lifecycle`. **Retire is terminal and destructive** (#347): it scrubs PII from `item_state`, clears the encrypted private blob, and wipes `item_locations` (`services/items/retire_pii.ts`); cancels every still-open connection on either side (`retire_connections.ts`); de-indexes the item from search (publishes a `delete` item-event); and **notifies the now-cancelled counterparties** (`notifications/notify_retire.ts`). Pause/unpause/retire all sweep the item-fetch caches — as does accepting profile consent (a `draft → live` promotion, #464, self *and* U18 guardian) — so a freshly-live/-retired item reflects immediately rather than after the cache TTL. **Every lifecycle transition also publishes an item event** (#557), not just retire: `item_search` is maintained by signals-search off those events and every read path there is live-only, so an unpublished `draft → live` leaves the profile invisible in each ranked feed and map viewport while `items` says live. Retire publishes `delete`; everything else publishes `upsert`. Any new path that changes `lifecycle_status` must publish too, **after** its transaction commits — see `.claude/rules/consent-v1.md`. **Which gates a profile must clear to reach `live` is per-domain config (#344):** `go_live_required` in `network.json` (`schema_required`, `consent_required` and/or `owner_required`; default `schema_required`). A `guardian_consent_required` domain must keep `consent_required` — config that dropped it would silently disable the U18 age control, so it is rejected at load.
- **U18 action gating (#395/#393).** A minor's action is blocked on any **external / on-behalf (aggregator) channel** — minors act **in-app only** — fail-closed in `services/guardian_action_gate.ts` (`channel: 'external' → MINOR_ACTION_CHANNEL_BLOCKED`); the **API gate is the control, not the UI**. A minor's *bulk* action is gated by **one batch guardian OTP** for the whole selection (scope = sha256 of the sorted action tuples), and the batch pre-pass is skipped on external channels so the external block still applies. The go-live consent gate itself lives in `.claude/rules/consent-v1.md`.
- **Discover / markers (search BFF).** `POST /api/v1/network/item/discover` is the ranked/searchable/filterable list feed (signals-search-backed; **falls back to a native distance/recency path when signals-search is down** — `q` + facets + radius still apply, only relevance *ranking* is lost). `/markers` serves the map viewport. When `item_search` has no rows for the network+domain (no signals-search worker in the environment), the bbox filter falls back to `items.item_locations` automatically and self-heals once the worker indexes its first row. Both restrict `q`/facet matching to **declared, non-private** `item_state` fields server-side (a private/undeclared field is dropped, never enumerable).
- **`x-reference-source` schema marker (#433).** A `network.json` field may carry `x-reference-source` (a bare `"colleges"` string, or `{ source, subtitle }`) to render a searchable autocomplete backed by an **external reference dataset** (`/reference/<id>.json`) instead of an inline enum — keeps large option lists out of the schema. The UI resolves the dataset via `VITE_COLLEGE_DATASET` / `VITE_REFERENCE_BASE_URL`; the stored value stays a plain string, so existing free-text values keep working. The marker is stripped before schema validation (client and server), so item validation is unaffected.
- **`x-uri` schema marker (#565).** A `network.json` item-schema field may carry `"x-uri": true` to declare that it holds a URL. Any number of fields per schema may be flagged. Two effects: (1) the profile/item cards render the value as a **clickable link** (`target="_blank" rel="noopener noreferrer"`) rather than plain text — an inline link in the field row, *not* an action button; (2) the shared `URL_PATTERN` from `packages/schemas/src/uri_fields.ts` is injected as a JSON Schema `pattern` on both the client (`schema-form.tsx`, before ajv) and the server (`validateAgainstJsonSchema`), so `companyabc` is rejected on the form *and* on the API. The scheme is optional (`example.com` is accepted and stored as typed; the card prefixes `https://` when building the href) and the empty string is allowed — use `minLength: 1` for a required link field. Also valid on an array-of-strings property, where the pattern lands on `items` and each entry renders as its own link. Masked values (`https://***`) and non-`http(s)` schemes are never linked. `pattern` is used rather than `format: "uri"` because the API's ajv registers no `ajv-formats` (so `format` is ignored on writes) and ajv's `uri` format rejects the scheme-less input users actually type. **Caution:** flagging a field that already holds non-URL data in live items will make **every** subsequent update to those items fail with `INVALID_ITEM_STATE`, not just an update that touches the flagged field — `computeItemStateUpdate` merges the submitted delta onto the full prior state and validates the whole thing (`apps/api/src/services/item_service.ts`). Audit the data before flagging a live field. The marker is stripped client-side before RJSF's ajv runs; server-side it is left in the schema and simply ignored, because that ajv runs with `strict: false`. Item validation is unaffected either way — but unlike `x-reference-source` above, the two sides are not symmetric here. **Known limits** (the form and the API share `applyUriPatterns`, so these apply to both): the transform walks `properties` and `items` but not `$defs`/`definitions`, so a field marked through a `$ref` gets no `pattern` and its validation silently does nothing — mark the concrete property, not a shared def. And the friendly error message is matched on top-level property names, so a marked field nested inside an object still validates but surfaces ajv's raw `must match pattern …` text. Server-side enforcement also does not apply to a field named in the schema's `required` array: `validateAgainstJsonSchema` omits those keys from the payload before validating (`ignoredKeys: required` at both `item_service.ts` call sites), so a required link field is validated on the form only — prefer marking optional fields until that omission is fixed.
- **`x-error-message` schema marker.** AJV's message for a failed `pattern` is the raw regex, which is meaningless to a user — and the regex lives in `network.json`, so a lookup table of known patterns in the UI would be wrong the moment a network adds an unfamiliar field. Any field may therefore carry `"x-error-message": "Enter a 10-digit mobile number, no spaces."` and the profile form shows that instead. Resolution order (`apps/ui/src/components/forms/field-error-message.ts`): the authored `x-error-message`, else the built-in URL copy for an `x-uri` field, else a generic naming the field ("Please enter a valid Mobile."). A raw regex is never shown, so a network that declares a bare `pattern` and no copy still reads sensibly. The marker is stripped before schema validation, so item validation is unaffected. Note the copy is applied on **both** error paths in `schema-form.tsx` — the pre-submit `extraErrors` path bypasses RJSF's `transformErrors` entirely, so each needs it.

## Workspace layout

pnpm + Turborepo monorepo. Workspace alias is `@dpg/*` → `packages/*/src` (note: package directory names like `auth`/`database`/`schemas` are imported as `@dpg/auth` etc.; some test configs alias additionally to plain workspace names — see `apps/api/vitest.config.ts`).

- `apps/api` — Fastify + Zod (`fastify-type-provider-zod`) + Drizzle ORM + better-auth + Redis. Entry: `src/server.ts`.
- `apps/ui` — React 19 + Vite, schema-driven (renders forms/cards from network + item schemas).
- `packages/config` — Zod env schemas (`secrets.ts`), allowed-origins lists, network-config loader, consent-config loader. **All env vars must be added here**, not parsed ad-hoc.
- `packages/database` — Drizzle setup, partition-aware query helpers.
- `packages/schemas` — shared Zod schemas (API request bodies, admin, consent, consent-config, schema registry).
- `packages/auth`, `packages/notification`, `packages/match_score` — service clients / config.

## Commands not covered in AGENTS.md

```bash
# Unit tests (API) — vitest, excludes *.integration.test.ts
pnpm --filter api test
pnpm --filter api test:watch

# Integration tests — opt-in, requires running db + redis
docker compose up -d db redis
pnpm --filter api test:integration

# Run one test file
pnpm --filter api exec vitest run src/path/to/file.test.ts

# Typecheck everything (api tsc + ui tsc, run sequentially)
pnpm typecheck

# Generate the deploy schema bundle (apps/api/db/postgres/schema.sql) + verify it matches checked-in copy
pnpm schema:bundle
pnpm schema:bundle:check
```

Root scripts wrap turbo via `scripts/turbo-with-root-env.mjs`. That wrapper exists so the root `.env` flows through to filtered packages — running `turbo run dev --filter=api` directly will miss env vars. Use the `pnpm dev:api` / `pnpm build:api` aliases unless you know why you're bypassing them.

`docker compose up -d db redis` brings up just Postgres + Redis. To containerize the API itself against those services: `DOCKER_NETWORK=dpg_internal pnpm docker:api`.

Node `>=24` and `pnpm@11.1.2` are pinned via `engines` / `packageManager`.

## UI Data Caching (React Query)

One QueryClient (`apps/ui/src/lib/query-client.ts`), one key factory
(`apps/ui/src/lib/query-keys.ts`). staleTime tiers: config-like data 5 min
(invalidate on change), browse feeds ~90s (+ `cache_ttl_seconds`), own data 60s
(+ invalidate-on-write), actions via `refetchInterval`. Geocoding uses dedicated
caches (Redis server-side, in-memory session client-side), not React Query.
Never rely on `refetchOnWindowFocus` for freshness.

**Deferred — instance-URL cache-busting (caching-spec §8):** when a
`selectedApiUrl` / instance switcher is added to the UI, switching it must bust
the React Query caches (browse/my-items/markers) and the client schema cache
(`clearSchemaCache`), because `createApiClient` captures `baseURL` at
construction. The `resolvedNetwork(networkId, apiBaseUrl)` key already carries
the API base URL. There is no switcher today, so no busting is wired yet.

**Active profile id in `browseItems` (caching-spec §8):** the selected
own-profile item id now anchors the discover list — it's forwarded to
signals-search as `anchor_item_id` and carried in the `browseItems` key in
discover mode, so switching profiles re-ranks and refetches (#394). It remains
**deferred for `markers`**: the map never calls discover, so relevance-ranked
map pins (P-follow-5) are still pending. See code comments at
`queryKeys.browseItems` and `queryKeys.markers`.

## Conventions worth highlighting

- **Files are snake_case.** Route handler exports are snake_case (`create_item`), internal handler functions are camelCase (`createItemHandler`). Zod schemas are PascalCase. DB columns are snake_case.
- **Routes never throw** — return `reply.code(N).send({ error, message })` with a machine-readable `error` code. Log with `request.log.error({ err, context }, 'message')`. Handle PG `23505` (unique) and `23503` (FK) explicitly.
- **ESM only**, strict TS, no `any`. Use `import type` for type-only imports.
- **No `console.log` in library packages** — go through `request.log` in app code.
- **No `// TODO` comments** — open an issue instead.

## Authoring pull requests

When you open a PR, include an **In Plain Terms** section in the description: a short, jargon-free explanation a non-expert teammate can follow — what the problem was and what the change does, in everyday language — alongside the usual Summary / Release Notes. Skip it only for a pure chore with no behavioural effect. This lives here as a Claude authoring rule rather than in the GitHub PR template on purpose, so PRs opened from other tools/flows aren't forced through it.
